# Grok 20.4.25 Release Verification

Date: 2026-11-11. GigaTIFF server 0.3.8 candidate, compared with the published
0.3.7 / Grok 20.4.19 image. No production stack was changed during testing.

## Build And Scope

Grok release `v20.4.25` is annotated tag
`ec841d383151c16f060d12c4f645193ca96bdbef`, source commit
`46ab34dee9590dcd97026e40e9ecd9383706bcad`. The candidate retains Rust 1.99.1,
the existing Cargo dependencies/release profile, Debian Trixie, classic Grok
(`GRK_MERCURY=0`) and the hybrid `auto` routing policy. Bindings are generated
from the installed Grok headers. Local z2000 experiments were excluded by
building from an isolated clean-source copy plus the release-version changes.

The full feature-enabled Linux workspace suite passed **67 tests**:
13 core, 6 desktop and 48 server tests. Zero tests failed or were ignored.
The container `verify` target also completed its binary/doc-test gates.

Host: Intel Core i5-14500, Docker Desktop Linux/amd64 on Windows. Each image
server had a four-CPU ceiling and 4 GiB RAM. Other host applications remained
running; this is a shared-host container regression test, not an isolated
codec microbenchmark. Native libraries installed by apt may also have changed
since the older image was built. Dependencies were not deliberately upgraded
in Cargo.lock, apart from the three workspace package-version entries.

## Corpus And Pixel Checks

The six unchanged RGB JP2 regression files are `cnb_user_bug.jp2`,
`mc_vkol-00b10d_0001.jp2`, `newspaper_master.jp2`, `newspaper_user.jp2`,
`small_master.jp2` and `small_user.jp2`. Dimensions range from 1589x994 to
3007x4701. Sizes, hashes and encoding context are retained in the earlier
[Grok investigation](2026-10-22-grok.md) and local raw sample metadata.
The multi-gigabyte maps and a broad archival ICC corpus were not tested here.

An additional synthetic 1024x768 RGB8 TIFF uses explicit **no compression**,
red/green/blue bars and a black grid. Three expected source colors and opaque
alpha are checked independently of the reference renderer.

Ten PNG cases per image cover full previews at widths 512/1024, native and
reduced 512-square tiles, large clipped windows, odd origins/dimensions and a
thin edge strip. Five server variants downloaded **350/350 successful PNGs**.

| Comparison | Cases | Maximum RGB Delta | Maximum Alpha Delta |
|---|---:|---:|---:|
| New Grok / new OpenJPEG | 70 | 1 | 0 |
| New Grok / old Grok | 70 | 0 | 0 |
| New hybrid / new OpenJPEG | 70 | 1 | 0 |
| New hybrid / old hybrid | 70 | 0 | 0 |

All **280 full-pixel RGBA comparisons passed**. Every candidate pixel has
alpha 255. All 84 additional concurrent PNG requests succeeded and were
pixel-exact against their serial output. No new block/stripe artifacts were
detected in the tested outputs. Passing this corpus is not general JPEG 2000
conformance certification.

## Sequential HTTP Benchmark

Response caching was disabled; process, metadata and filesystem caches were
warm. These are not cold-disk or first-process-start timings. Each of six
scenarios on six JP2 files was measured over three rounds, reversing variant
order on alternate rounds: **540/540 HTTP responses were successful**.

For each file/scenario, use its three-round median. The geometric mean of 36
paired new/old ratios is:

| Mode | HTTP Latency Ratio | Render Latency Ratio |
|---|---:|---:|
| Explicit Grok, one decoder thread | 0.973 | 0.968 |
| Hybrid, adaptive OpenJPEG budget <=4 | 1.000 | 0.963 |

A value below 1 means lower latency. The differences are small on this shared
host and do not establish a performance improvement. There is no material
aggregate HTTP regression on this workload. Explicit Grok is fixed at one
thread; passing `--openjpeg-threads 4` does not make Grok four-threaded.

Pooled HTTP medians in milliseconds, 18 observations per cell:

| Scenario | Hybrid New | Hybrid Old | Grok New | Grok Old | OpenJPEG New |
|---|---:|---:|---:|---:|---:|
| Full -> width 512 | 113.86 | 107.72 | 114.34 | 120.21 | 127.29 |
| Full -> width 1024 | 349.67 | 311.47 | 521.70 | 479.39 | 386.87 |
| 512 square -> 512 | 70.47 | 69.00 | 73.16 | 71.47 | 81.08 |
| 512 square -> 128 | 28.18 | 27.35 | 23.65 | 24.03 | 46.34 |
| Center <=4096 -> width 512 | 112.83 | 124.53 | 116.72 | 125.59 | 128.91 |
| Edge <=4096 -> width 512 | 125.66 | 118.04 | 120.15 | 126.85 | 136.06 |

Paired ratios are not ratios of these pooled medians. Large-window regions are
clipped to each source, and output preserves aspect ratio. Individual cases
vary, including higher pooled full1024 latency; three rounds do not provide
confidence intervals or a production capacity estimate.

## Pre-Existing Compressed-TIFF Failure

The initial wider test used System.Drawing's default TIFF compression. Its
metadata is RGB8 LZW, one strip, 768 rows per strip. Eight of ten PNG scenarios
failed in **both 0.3.7 and 0.3.8**, regardless of the JP2 backend selector:

```text
Compression algorithm does not support random access.
libtiff failed to read scanline 4
```

The full1024 and native top-left 512-square cases succeeded; sampled/offset
access within the compressed strip failed. This is an existing libtiff
scanline-access limitation, not a regression introduced by Grok 20.4.25.
The first failed run and compressed source were preserved separately. They
are **not counted as passed TIFF tests**. The subsequent passing matrix
explicitly uses an uncompressed TIFF. Repairing compressed multi-row-strip
access remains a separate core-renderer task; this release does not fix it.

## Evidence And Reproduction

### Published Image Verification

After the successful [GHCR workflow](https://github.com/bezverec/gigatiff-kramerius-stack/actions/runs/42997301927),
the published `ghcr.io/bezverec/gigatiff-server:0.3.8` image was pulled and the
complete artifact matrix repeated, without repeating timing measurements.
Its OCI index digest is
`sha256:ec53ca6139feee7d65743937fc74931220faf2d7a42adf8c4187af065528a9a5`
and source revision is `d75c529e2178b3985672285b7a20ef0517950425`.
Anonymous registry access, revision/version labels, `GRK_MERCURY=0`, SPDX SBOM
and SLSA provenance were verified independently of Docker credentials.

All **350 PNG requests**, **280 full-image RGBA comparisons** and **84 concurrent
PNG requests** passed again. Old/new Grok and hybrid outputs were pixel-exact;
Grok versus OpenJPEG had a maximum RGB delta of one, zero alpha delta and no
non-opaque pixels. The uncompressed TIFF's expected RGB colors also passed.
The known compressed-TIFF limitation above is unchanged. Evidence is retained
locally under `published-results/`; the tests stopped their own containers
and did not modify the running ZimaBoard installation.

### Local Harness

Local ignored evidence is under `target/grok-20.4.25-20261111/`:
`run.ps1`, `pixels.ps1`, `analyze.ps1`, `fixtures/`, `results/validation.json`,
`pixel-downloads.json`, `pixels.json`, `concurrent-pixels.json`, `http.json`,
`batch.json` and `summary.json`. The first attempt is retained in
`results-compressed-tiff-baseline/` and `compressed-tiff-attempt.log`.
Payload TIFF/JP2/PNG files are not committed to the repository.

From the GigaTIFF checkout, with the two local release images and fixtures
available, the harness can be rerun with:

```powershell
& ./target/grok-20.4.25-20261111/run.ps1
& ./target/grok-20.4.25-20261111/analyze.ps1
```

The harness validates its own PNG, pixel, alpha, concurrency and timing counts,
checks expected TIFF colors, waits for the completed workspace test gate,
and stops only its owned containers. It does not publish or deploy images.
