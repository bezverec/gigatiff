# Grok 20.4.19 First-Load Investigation

Date: 2026-10-22. Local tests only; no registry publication or ZimaBoard deployment.

## Conclusion

The dominant slowdown comes from Grok's **embedded Mercury decode path**, not
the updated GigaTIFF Rust dependencies. Keeping Grok 20.4.19 and the new crates,
but setting `GRK_MERCURY=0`, restores approximately the old decode performance.
This still uses **Grok FFI**, not an OpenJPEG fallback.

For the earlier regression sample, Grok 20.4.15 logs:

```text
mercury fastpath bail: plan rejected: Logic("plan: unsupported code-block modes (Cmodes 0x1)")
```

It then uses Grok's classic pipeline. The newer Mercury supports BYPASS/TERMALL
code-block modes and no longer rejects that sample at this early gate. Thus a
version upgrade changes the internal pipeline used for an otherwise identical
request. Disabling Mercury removes the dominant regression on all six tested
files. This does not establish which individual Mercury planning/decoding stage
accounts for the remaining latency, nor is it a commit-by-commit performance bisect.

Mercury is compiled into libgrokj2k when Cargo is available at Grok configure
time. It need not appear as a separate GPU plugin in process library maps.
`cpu_only` controls plugin acceleration; it is not the embedded-Mercury opt-out.
See the upstream [Mercury fast-path implementation](https://github.com/GrokImageCompression/grok/blob/31ae6fa25be3747370b47a65d311e355f2adb33f/src/lib/core/mercury_fastpath.cpp),
[CMake configuration](https://github.com/GrokImageCompression/grok/blob/31ae6fa25be3747370b47a65d311e355f2adb33f/src/lib/core/CMakeLists.txt),
and [Part 1 code-block mode support change](https://github.com/GrokImageCompression/grok/commit/217347614b0b0554b511acd4a5e24ac024c14589).

## Controlled Matrix

Four images crossed Grok 20.4.15/20.4.19 with the old/new GigaTIFF Cargo manifests
and lockfiles. All used the same current FFI implementation, including
`num_threads = 1` per codec, Rust 1.99.1, build flags, native build environment,
and dated Debian Trixie runtime. Only the selected Grok source and Cargo files
varied; the old manifest also retains its old package-version metadata.

- Old Cargo files: GigaTIFF commit `8fd39ef8babad5dae1aace5d7eeda9c586353f36`.
- Grok 20.4.15: `cadd794339974e9350bbfc9db6e5756d3d25b07d`.
- Grok 20.4.19: `31ae6fa25be3747370b47a65d311e355f2adb33f`.
- Linux amd64 on Docker Desktop; kernel `6.6.87.2-microsoft-standard-WSL2`.
- Four-CPU container limits; single-thread Grok decoders; four concurrent HTTP render slots.
- Samples mounted read-only; encoded response cache disabled; HTTP output lossless WebP.
- Each Grok was rebuilt against its own headers under `/opt/grok`; `ldd` verified
  that the intended library was loaded. Shared libraries were not blindly swapped.

The direct `bench-grok` example measures codec setup/header/decode and RGBA
conversion separately, excluding HTTP, final resizing and output encoding.
Output sizes are reduction hints: the returned decoded bitmap may be larger
than the requested final size. Geometry matched across all four variants.

The FFI matrix used six files, four request shapes, three alternating-order
rounds and five measured iterations after one excluded warm-up per invocation:
**1,440 measured decodes**. Each file/shape/variant has 15 samples. The table
below pools 90 samples per cell; all values are median decode milliseconds.

| Source Window / Output Hint | Grok 15, Old Crates | Grok 15, New Crates | Grok 19, Old Crates | Grok 19, New Crates |
| --- | ---: | ---: | ---: | ---: |
| Full / 512 | 102.06 | 97.84 | 283.90 | 294.82 |
| Full / 1024 | 364.52 | 340.77 | 858.61 | 826.85 |
| 512 / 128 | 18.67 | 18.89 | 58.09 | 56.94 |
| Clipped 4096 / 512 | 101.36 | 98.17 | 251.50 | 246.68 |

For attribution, first take each file/shape median, then pair the same request
across variants. The median ratios across 24 pairs are:

| Change | New / Old Decode Time |
| --- | ---: |
| Grok 15 to 19, old crates held fixed | 2.9320 |
| Grok 15 to 19, new crates held fixed | 2.9214 |
| Old to new crates, Grok 15 held fixed | 1.0057 |
| Old to new crates, Grok 19 held fixed | 1.0030 |

The dependency-only medians are within normal run-to-run noise here; this is
not a claim that every individual dependency or request has zero effect.
RGBA conversion did not show the large slowdown. Since the new compiler and
runtime are held fixed and old Grok remains fast, they cannot by themselves
explain the observed multi-fold difference.

## Mercury Intervention

The *same* Grok 20.4.19/new-crates binary was then measured with
`GRK_MERCURY=1` versus `GRK_MERCURY=0`. Two alternating-order rounds and three
iterations per file/shape produced **288 measured decodes**, 36 per table cell.

| Source Window / Output Hint | Mercury Enabled | Classic Grok | Unit |
| --- | ---: | ---: | --- |
| Full / 512 | 233.19 | 96.41 | ms |
| Full / 1024 | 732.02 | 329.16 | ms |
| 512 / 128 | 57.07 | 15.72 | ms |
| Clipped 4096 / 512 | 255.12 | 91.75 | ms |

The median paired Mercury/classic decode-time ratio is **2.9553** across the
24 file/shape pairs. For `cnb_user_bug.jp2`, a full/512 request takes roughly
500 ms on the Mercury path versus 100 ms on classic Grok in the diagnostic run.

A further HTTP comparison interleaved two passes of old Grok/new crates and new
classic Grok/new crates. Values below are median client milliseconds across six
files and two passes, 12 observations per cell:

| Request | Grok 20.4.15 | Grok 20.4.19, Mercury Off |
| --- | ---: | ---: |
| Full to 512 | 116.8 | 118.5 |
| Full to 1024 | 430.0 | 449.0 |
| 512 to 128 | 24.4 | 22.8 |
| 4096 to 512 | 109.6 | 116.2 |
| Advertised tile | 107.8 | 115.6 |
| Four-request startup batch | 74.9 | 86.8 |
| Startup viewport | 285.9 | 191.1 |
| Prewarmed startup viewport | 357.3 | 208.1 |

All responses were HTTP 200 and image responses reported `grok-ffi`. Viewer and
prewarm timings are noisier than isolated decodes; do not interpret their
differences as a universal improvement. Other services ran on the PC and the
OS page cache was not flushed. These are not ZimaBoard timings.

## Negative Allocator Control

The new 2 MiB alignment / `MADV_HUGEPAGE` change was tested independently using
a local, process-scoped diagnostic interposer. One complete balanced pass of
216 measured decodes compared the unmodified calls, skipping only the huge-page
hint, and restoring 64-byte alignment while skipping that hint. An interrupted
partial second pass is excluded from the summary.

Neither intervention removed the regression. The slow `cnb_user_bug.jp2`
full/512 request made zero huge-page alignment/hint calls, while full/1024 did
make such calls but remained slow when they were intercepted. WSL2 had THP and
defrag both in `madvise` mode. This rules out the new allocator branch as the
dominant explanation for these requests. No kernel setting was changed and the
diagnostic interposer is not part of the product or recommended workaround.

## Pixel Checks

Six 36-case suites completed: **216 successful comparisons**, maximum channel
delta 1. They cover full/512 plus full-resolution, reduced, center and edge
regions on each sample.

- Changing only the Cargo files with Grok 15: 36/36 pixel-identical.
- Grok 19 with either Cargo set versus Grok 15: 36/36 within delta 1 per suite.
- New classic Grok versus old Grok: 36/36 pixel-identical.
- New classic versus new Mercury: 36/36 within delta 1, 18 exact.
- The original local `localhost/gigatiff-server:0.3.7` image, started with
  `GRK_MERCURY=0`, versus old Grok: 36/36 pixel-identical, all `grok-ffi`.

The last check confirms that the opt-out works without rebuilding the existing
local candidate. No known block/checkerboard artefacts appeared in this suite.
Lossy decoder rounding differences must not be mislabeled as pixel identity.

Samples: `cnb_user_bug.jp2`, `mc_vkol-00b10d_0001.jp2`,
`newspaper_master.jp2`, `newspaper_user.jp2`, `small_master.jp2`, `small_user.jp2`.
The multi-gigabyte map masters and a broad HTJ2K/mode-0 corpus are not covered.

## Reproduction And Scope

Build the low-level example on Linux with the desired Grok SDK installed:

```bash
cargo build --release --locked -p gigatiff-core \
  --features jpeg2000-grok-ffi --example bench-grok
GRK_MERCURY=0 ./target/release/examples/bench-grok sample.jp2 \
  --width 2761 --height 3870 --out-width 512 --out-height 717 --iterations 5
```

Use the actual full-resolution window dimensions of your sample. Repeat with
`GRK_MERCURY=1`, then compare the decode and conversion columns independently.
For Docker, scope `--env GRK_MERCURY=0` to the image-server container; do not
change system-wide environment settings or substitute OpenJPEG for this test.

Complete local recipes, old Cargo snapshots, build logs, sample SHA-256 hashes,
raw CSV/JSON and PNG comparisons are under ignored `target/grok-regression/`.
`Matrix.Dockerfile`, `run-matrix.ps1`, `run-mercury.ps1` and `summarize.ps1`
record this local experiment. The sample files are not committed.

Keep the new Rust dependencies and retain the hybrid `auto` backend policy.
The runtime Mercury opt-out is a measured candidate for low-latency JP2 serving,
not a universal verdict on Mercury. Validate representative large masters,
other coding modes, concurrency and native Linux before making it a production
default. The exact Mercury-stage bottleneck remains a profiling task.
No production defaults, deployed stack, Git refs, releases or registry images
were changed by this investigation.
